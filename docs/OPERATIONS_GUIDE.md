# 운영 가이드

## 일상 실행

Windows 작업은 평일 09:50에 시작하며 Python이 한국 시각 목표(기본 10:00)까지 준비 후 대기합니다. Windows 로그인 세션, 네트워크, 시간대 설정을 확인하세요. 휴일에는 `SKIPPED`로 종료합니다. 늦게 부팅한 PC에서 놓친 작업을 자동 보상하거나 종료된 전체 작업을 반복 실행하지 않습니다.

예약일은 사이트의 납품예정일 선택값입니다. 실행일과 다를 수 있으므로 결과의 `day`를 확인하세요. 이 프로그램은 청북2층·일반품목·미선택 납품허용(`O`) 자급자재 3개 추가·파렛트 1·차량 1을 대상으로 합니다. 기존 체크는 유지합니다. 기존 예약번호가 있어도 시간대 체크박스가 활성화되어 있으면 품목을 먼저 조회하고 추가를 진행하며, 기존 파렛트·차량 수는 유지합니다. 예를 들어 기존 3개가 선택되어 있으면 3개를 추가하여 총 6개로 진행하며, 추가 가능한 항목이 3개 미만이면 기존 선택을 유지한 채 중단합니다.

자급자재 팝업의 기존 체크 수는 조회 조건에 따라 메인 예약의 전체 품목 수보다 적을 수 있습니다. 팝업은 기존 체크 수 + 3개, 메인 예약창은 기존 전체 품목 수 + 3개로 각각 확인한 후 저장 버튼을 누릅니다. 예를 들어 메인에 8개가 있고 팝업에 기존 1개만 조회되면 팝업은 4개, 메인은 11개가 됩니다. 저장 시 품목 수 한도는 사이트가 검증합니다.

## 결과 확인

`logs/YYYYMMDD/HHMMSS_ffffff/result.json`에서 전체 상태, 종료 코드, 시간대별 결과와 예약번호를 확인합니다. 같은 폴더의 HTML은 로그 수준 필터와 검색을 제공하며 `[COMPLETE]`가 최종 요약입니다. 시간대별 텍스트 로그는 `13/automation.log` 등, 스크린샷은 `attempt_1/13/` 등에 있습니다. 팝업 순서에 영향을 주는 resize 이벤트를 피하기 위해 전체 페이지 대신 현재 화면 범위만 캡처합니다.

- `CONFIRMED`: 저장 응답과 새 예약 목록의 예약번호가 일치합니다. 이전 로컬 확인 기록을 유지한 경우도 포함합니다.
- `WAIT`: 대기 등록까지 확인했습니다. 예약 확정과 다릅니다.
- `UNKNOWN`: 저장 결과를 확정할 증거가 부족합니다. 실패로 단정해 다시 저장하면 안 됩니다.
- `SUBMITTING`: 동작 중이거나 중간에 프로세스가 종료됐습니다.
- `EXISTING`: 이전 버전이 기존 예약번호 때문에 중단한 결과입니다. 현재는 활성화된 시간대의 기존 예약에 자재 추가를 진행합니다.
- `FAILED`: 준비 실패 또는 명시적 거절입니다.

종료 코드 0은 전체 확정/점검 완료/휴일 생략, 1은 실패, 2는 부분 완료 또는 운영자 확인 필요입니다. 스케줄러의 `0x0`과 스크린샷만으로 납품 예약 확정을 판단하지 마세요. 서버 예약 내역이 최종 기준입니다.

## 재실행

1. 서버에서 실제 예약일·시간·창고·예약번호와 대기 여부를 확인합니다.
2. 미처리 시간만 `run_automation.bat --hours 14 15 --headful`로 실행합니다.
3. `UNKNOWN`이며 서버에 미등록인 것이 확인되었으면 해당 시간에 한해 `--hours 14 --retry-unknown`을 추가합니다.
4. `SUBMITTING`은 재시도 옵션으로도 덮어쓰지 않습니다. 작업 관리자에서 실행 중인 프로그램을 확인하고, 서버 처리 여부와 `logs/reservation_state.sqlite3`의 해당 기록을 운영 담당자가 함께 검토합니다. DB 전체 삭제는 재신청 방지 기록을 잃게 하므로 사용하지 않습니다.

예약 전 단계 실패만 목표 시각 이전에 최대 5회 복구합니다. 저장이 시작된 후에는 일부 성공 시간대를 포함한 전체 자동 재시도를 하지 않습니다. 동시에 실행해도 같은 DB의 저장 권한은 시간대별로 한 실행만 획득합니다. 서로 다른 PC나 다른 로그 폴더에는 이 제약이 공유되지 않습니다.

## 안전한 점검

```bat
run_automation.bat --check-config
run_automation.bat --headful --force --dry-run
```

첫 명령은 로컬 설정만 검사합니다. 두 번째는 로그인·조회와 저장 전 폼 입력을 점검하며 대기 시각과 최종 저장을 생략합니다. `--force` 자체는 예약을 막지 않습니다. 슬롯이 닫혀 있으면 준비 점검이 실패할 수 있습니다.

## 기록 관리

실행 기록은 자동 삭제하지 않습니다. HTML이 참조하는 스크린샷도 함께 보관하세요. `reservation_state.sqlite3`는 결과 폴더와 함께 보존합니다. 로그는 실행 중 파일에 기록하지만 강제 종료 직전 큐의 일부 메시지는 남지 않을 수 있습니다. 저장 직전 상태는 별도 SQLite 트랜잭션으로 남깁니다.

설정 목록과 상태별 의미는 [README](../README.md)를 참고하세요. 계정 설정은 기존 설정 마법사 또는 `config.json`을 사용합니다.
